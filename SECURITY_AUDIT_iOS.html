✅ 安全亮点

🔐 Keychain 密钥管理

API Key 存储在 Keychain（kSecAttrAccessibleWhenUnlockedThisDeviceOnly），为每个 profile 分槽（api-key / api-key.<profileId>），完全符合 iOS 安全标准。密钥永不进入日志。

📋 配置隐私

profile 与全局设置存 UserDefaults，敏感字段（API Key）独立用 Keychain 管理。配置不落盘明文敏感信息。

🛡️ HTTPS 首选

URLSession 默认走系统证书验证。自签证书信任仅在用户显式开启内网模式且内核判定为私网时才启用。

🔄 版本迁移

旧版配置无缝迁移到 profile 体系，首次启动自动转换，用户无感知。Keychain 账号兼容（api-key）避免升级后 Key 丢失。

⚙️ URLSession 配置

禁用 Accept-Encoding 压缩以保证 SSE 增量到达、请求和资源超时分别为 120s 和 300s，防止长连接漂移。每个请求一个独立 session + delegate，无回调串联。

📍 Info.plist 权限声明

权限声明清晰：位置、麦克风、相册都有用户可见的提示，符合 App 审核要求。后台模式仅 audio + fetch（日程提醒）。

⚠️ 发现的问题

高优先级 (1 项)

自签证书验证缺少私网地址校验
HIGH
位置： AiSettingsStore.swift 第 600-613 行 + AiTransport.swift 第 103-115 行

问题描述： iOS 侧自签证书信任的防御层级相对单薄。设计流程为：
  • 用户开启"允许自签证书"开关（存 UserDefaults）
  • Swift 侧根据此开关挂上 TrustAllDelegate
  • 内核只检查「地址是否私网」，但该检查发生在共享代码里（Android Kotlin）
  • iOS 侧没有单独验证地址是否私网
若共享内核的私网验证有漏洞，或如果用户无意中配置了公网地址的自签证书，iOS 会盲目接受。
建议：
  • 在 AiTransport.swift 的 start() 中，自签证书启用前再做一次私网地址检查
  • 复用或适配内核的 AiNetworkPolicy.isPrivateHost() 逻辑到 iOS 侧
  • 如果 host 不是私网，直接拒绝而非交给 delegate
  • 优先级：立即修复（防止证书 MITM 漏洞）

中优先级 (1 项)

模型列表获取的自签证书逻辑与流式请求不一致
MEDIUM
位置： AiSettingsStore.swift 第 600-613 行（AiModelCatalog.TrustAllDelegate）

问题描述： AiModelCatalog.fetch() 中的 TrustAllDelegate 与 AiTransport.swift 中的实现不同：
  • AiModelCatalog：直接 .useCredential 接受任何自签证书（**无私网验证**）
  • AiTransport：依赖 request.allowSelfSigned（内核已判定）
两者防御等级不对等。`fetch()` 方法虽然传入了 `allowSelfSigned` 参数，但未用来保护 delegate 本身。
建议：
  • 统一两处的 Delegate 实现，都在业务层做私网验证
  • 或将验证逻辑提取为单一 Delegate 类，两处复用
  • 在 fetch() 方法中添加 URL host 私网检查
  • 优先级：下个 Sprint 统一

🔎 详细分析

项目结构

  • 语言： Swift 5.9+ (iOS 16+)
  • 架构： Kotlin Multiplatform（共享 `Shared` 模块）+ iOS UI 层
  • 源文件数： 51 个 Swift 文件
  • 关键模块： AI 聊天、APRS/FT8/CW、位置、提醒、QSO 日志

数据存储与加密

数据类型 存储位置 保护方式 状态

Profile 配置 UserDefaults JSON 编码（明文） ⚠️

网络通信

URLSession 配置：

  • 请求超时： 120 秒（保证流式 SSE 不中断）
  • 资源超时： 300 秒（完整响应）
  • 压缩： 禁用 Accept-Encoding（SSE 需增量）
  • HTTPS 证书： 系统 CA 校验（默认）
  • 自签证书： 仅当用户开关 + 内核判定私网时接受（**需加强**）

与 Android 的对比

🔐 密钥存储

Android Android Keystore + AES-256-GCM
iOS Keychain（系统管理）
结论： 两者都符合平台最佳实践，安全等级相当

🛡️ HTTPS 与自签证书

Android manifest 禁止 + 业务层验证（**双层防御**）
iOS URLSession 默认验证 + delegate 仅信用内核（**单层**）
差异： iOS 应在业务层补充私网验证

📱 权限管理

Android AndroidManifest + 运行时权限
iOS Info.plist 用途说明 + 系统弹窗
结论： iOS 声明清晰，符合 App Store 要求

代码质量检查

  • 硬编码密钥： ✅ 未发现，所有 API Key 通过 Keychain 或参数传递
  • 不安全序列化： ✅ 使用 Codable（不用 NSCoding）
  • 日志泄露： ✅ 未发现在 print / NSLog 中输出敏感信息
  • 弱密码： ✅ 使用系统 Keychain 访问控制
  • 不安全反射： ✅ 未使用 Mirror 或 Objective-C runtime

第三方依赖

iOS 应用基于 Kotlin Multiplatform 架构：

  • 共享模块（Kotlin）： 所有依赖与 Android 同步（已审核）
  • iOS 层（Swift）： 无额外第三方依赖（仅系统框架）
  • 系统框架： Foundation, URLSession, Security, Combine 等（苹果官方）

结论： 无已知 CVE 风险

🎯 总结与建议

与 Android 的一致性

iOS 和 Android 分支采用 Kotlin Multiplatform 架构，共享业务逻辑。两个平台的安全设计理念一致，但实现细节有差异：

方面 Android iOS 建议
明文 HTTP manifest 双层禁止 URLSession 系统验证 一致 ✅
自签证书 业务层验证私网 只信任内核判定 iOS 需补强 ⚠️
敏感数据 AES-256-GCM Keychain（仅 Key） iOS 考虑扩展 ✓
