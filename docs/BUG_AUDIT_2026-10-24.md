## 🔴 P1 — 功能错误（6 项）

### P1-1 ✅ PD-290 的 VIS 码写成 0x64，正确值为 0x5E (94)

- **位置**：[SstvMode.kt:420](../app/src/main/java/com/example/hamkit/data/sstv/SstvMode.kt#L420)
- **现象**：文件头注释（L193）自称「PD-290=94(0x5E)」，枚举却写 `visCode = 0x64`。经与 pySSTV（`PD290.VIS_CODE = 0x5e`）、slowrx `modespec.c` VIS 表（0x5D=PD50、0x5E=PD290、0x5F=PD120）核对，0x5E 为正确值，0x64 未被任何权威表分配。
- **触发与影响**：
  - 接收：真实 PD-290 信号 VIS 校验通过后 `fromVisCode(0x5E)` 查不到模式 → 按「未收录模式」停止接收；
  - 发射：广播错误 VIS 码，对端解码器无法识别。
- **修复方向**：`PD_290` 的 `visCode` 改为 `0x5E`；补一条「各枚举 visCode 唯一且与头注释数值一致」的单元测试防回归。

### P1-2 ✅ 接收录音全程零写入，产出空 WAV

- **位置**：[SstvRecorder.kt:194](../app/src/main/java/com/example/hamkit/data/sstv/SstvRecorder.kt#L194)
- **根因**：`SstvWavRecorder.append(samples, offset, count = samples.size - offset)`，调用处 `append(pending, pendingCount)` 把本应是 count 的值传到 offset 位。`pending.size == pendingCount` ⇒ 计算出 `count = 0` ⇒ `append` 内 `if (n == 0) return` 直接返回。
- **触发与影响**：每次 `flushRecording` 均为零写入；`closeRecording` 只落一个 `dataSize = 0` 的 44 字节头。**「接收录音」默认开启，全程音频静默丢失**，用户事后重解（一键重解功能）拿到的是空文件。
- **修复方向**：改为 `append(pending, 0, pendingCount)`；补「录音文件样本数 > 0」回归测试。

### P1-4 ✅ APRS 会话列表整体不可用，未读标记永不生效

### P1-5 ✅ 消息不校验收件人是否本台，范围内任意消息都入库并回 ACK

- **位置**：[AprsViewModel.kt:384-411](../app/src/main/java/com/example/hamkit/ui/viewmodel/AprsViewModel.kt#L384-L411)
- **根因**：`handlePacket` 对 `:DEST:body{N}` 分支不判断 `parsed.destination == config.fullCallsign` 就 `insertMessage` + `sendAck`。默认 `r/35/105/1000` 过滤下，范围内台站间聊天（如 `:OTHER-1 :hi{1}`）全部涌入本机会话列表，并对第三方会话意外应答 ACK。
- **影响**：会话列表被无关流量污染；对他人会话回 ACK 违背 APRS 消息协议语义。
- **修复方向**：入库与回 ACK 前校验 `destination == config.fullCallsign`（呼号+SSID 精确匹配），其余消息忽略或仅计数。

### P1-6 ✅ 通知深链 intent 在 Activity 重建后重新解析，SSTV 页重复入栈

- **位置**：[MainActivity.kt:326-345](../app/src/main/java/com/example/hamkit/ui/MainActivity.kt#L326-L345)
- **根因**：`onNewIntent` 调 `setIntent(intent)` 固化通知 extra；Activity 无 `configChanges`，旋转/进程恢复后 `onCreate` 再次解析同一 intent → `pendingSstvLaunch` 重新置值 → `LaunchedEffect` 无条件 `push`。返回栈已由 Saver 恢复为 `[Main, SstvMain]`，每转一次屏叠一层。
- **修复方向**：消费后从 intent `removeExtra`（或 `setIntent` 剥离 extra），或 `onCreate` 仅在 `savedInstanceState == null` 时解析。

## 🟡 P2 — 边界或偶发（15 项）

### P2-1 ✅ 持续接收：解码器被多协程无同步并发访问

- **位置**：[SstvViewModel.kt:1199](../app/src/main/java/com/example/hamkit/ui/viewmodel/SstvViewModel.kt#L1199)、[1252](../app/src/main/java/com/example/hamkit/ui/viewmodel/SstvViewModel.kt#L1252)
- **要点**：采集协程（IO）调 `feed/feedAudio`；预览刷新协程（Default）每 120ms 调 `stats()`；停止收尾在 join 3 秒超时后仍调 `finalizeFrames()`（此时采集协程可能尚活着）。解码器自述「不是线程安全的」，全部可变字段无同步原语。
- **影响**：脏统计、低概率崩溃。
- **修复方向**：解码器内部加锁（参照 `SstvRollingImage`），或把 stats/finalize 读取收敛到采集协程同一作用域。

### P2-2 ✅ 月球位置历元常数混搭，系统性偏差约 19.8°

- **位置**：[CelestialComputer.kt:304](../app/src/main/java/com/example/hamkit/data/satellite/CelestialComputer.kt#L304)
- **要点**：月球平黄经等四个角度系数取 Meeus J2000.0（JD 2451545.0），`d` 却用 Schlyter 基准 `jd - 2451543.5`，少减 1.5 天 → 每角偏差 1.5 × 13.176 ≈ 19.8°。数值验证（2026-10-24）：代码 L′=80.6°，若配 J2000 历元为 60.9°，两者恰差 19.76°。太阳公式用 `jd - 2451545.0` 正确，仅月球错。
- **影响**：蚀（地影）判断、月相/月亮方位显示的精度损失。
- **修复方向**：`val d = jd - 2451545.0`，与 Meeus 常数配套。

### P2-3 ✅ APRS 断线重连计数失效：两种时序都与设计相悖

- **位置**：[AprsConnection.kt:42-99](../app/src/main/java/com/example/hamkit/data/aprs/AprsConnection.kt#L42-L99)
- **要点**：`reconnectAttempts` 只在成功建连后清零、在循环尾条件块内自增。首连即失败时 catch 直接落回循环，attempts 恒 0 → 无退避无限原地重试；成功后断线时 attempts 已被清零但自增块的条件/顺序使一次断开即永久放弃重连。
- **修复方向**：catch 分支内 `reconnectAttempts++`，成功建连后清零，统一退避路径。

### P2-4 ✅ APRS 消息无去重，洪泛/积压重复包重复入库

- **位置**：[AprsViewModel.kt:388-399](../app/src/main/java/com/example/hamkit/ui/viewmodel/AprsViewModel.kt#L388-L399)
- **要点**：入库前不按 `(source, msgNumber)` 查重；APRS-IS 洪泛与重连后的历史积压都会形成重复气泡，未读数虚增。
- **修复方向**：入库前查同 source+msgNumber 近期记录，或建唯一约束。

### P2-5 ✅ ack/rej 前缀判定过宽，正文以 ack 开头的普通消息被吞

- **位置**：[AprsPacketParser.kt:73-74](../app/src/main/java/com/example/hamkit/data/aprs/AprsPacketParser.kt#L73-L74)
- **要点**：`cleanBody.startsWith("ack")` — 正文 `acknowledged, plz resend` 会被判为 ACK；带 msgNumber 时正文被吞且外发消息被误标已送达。
- **修复方向**：按协议收紧为全串匹配 `ack` + 1~5 位字母数字。

### P2-6 ✅ msgCounter 仅内存态，进程重启归 1 与旧编号冲突

- **位置**：[AprsViewModel.kt:264](../app/src/main/java/com/example/hamkit/ui/viewmodel/AprsViewModel.kt#L264)
- **要点**：`markAcknowledged` 按 `(destination, msg_number)` 匹配无时间窗；重启后新消息编号与离线队列旧编号重叠，ACK 可误标到错误记录。
- **修复方向**：初始化时从库取历史最大编号续起；配合 P2-4 的去重。

### P2-7 ✅ APRS 地图 marker 增量添加后坐标永不更新

- **位置**：[AprsMapScreen.kt:136-161](../app/src/main/java/com/example/hamkit/ui/screen/aprs/AprsMapScreen.kt#L136-L161)（两套 UI 相同）

- **修复方向**：按呼号缓存 Marker 引用，坐标变化时 `setPosition` 更新。

### P2-8 ✅ 连接失败/断线后前台服务与常驻通知残留

### P2-9 ✅ 播放捕获期间前台服务被回收后，接收无法自动恢复

### P2-10 ✅ 接收进行中导入/重解录音会吞掉本次及后续帧的自动保存

### P2-11 ✅ ReminderStore 读-改-写无锁，与后台 Worker 并发可复活已删提醒

### P2-12 ✅ APRS 发送间隔允许输入 0，形成定位+发报紧循环

### P2-14 ✅ MainViewModel.initialized 前置置位，初始化被取消后永久跳过

### P2-15 ✅ 摩斯「U 前缀」转码双向歧义：往返不还原甚至解码越界

- **位置**：[MorseCodeScreen.kt:88-89, 103-119](../app/src/main/java/com/example/hamkit/ui/cw/MorseCodeScreen.kt#L88-L119)
- **要点**：编码对表外字符（含 U 自身）用 `U 前缀 + hex`；解码见 `..-` 即吞后续 hex 码组拼码点。含 U 的纯字母消息往返后内容被改写；hex 串 >6 位或超 Unicode 范围时 `parseInt/appendCodePoint` 抛异常。
- **修复方向**：转义设计重做（仅编码路径可产生的转义），解码校验 hex 长度与码点合法性，非法按普通字符处理。

## 🔵 P3 — 体验或一致性（9 项）

### P3-1 ✅ 轨迹历史清空分支永不执行（死逻辑）

- **位置**：[LiveSatelliteTracker.kt:152-162](../app/src/main/java/com/example/hamkit/data/satellite/LiveSatelliteTracker.kt#L152-L162)
- **要点**：只有 `elevation > -5.0` 的点会进 buffer，清空分支却要求 `last().second <= -5.0` 才清 → 条件永假。卫星再次升起时新旧轨迹段相连，画出跨时间折线。
- **修复方向**：首次跌破 -5° 即清空 buffer，删掉基于 last 点的判断。

### P3-2 ✅ 过境最大仰角精化窗口过窄，可能漏掉真实峰值

- **位置**：[SatellitePredictor.kt:383-384](../app/src/main/java/com/example/hamkit/data/satellite/SatellitePredictor.kt#L383-L384)
- **要点**：粗扫描 5 分钟步长，精化仅在命中点 ±5 分钟；峰顶距采样点超过 5 分钟时真实峰值不被采样，maxElevation 偏低，影响列表排序。
- **修复方向**：精化窗口覆盖粗扫描一个完整步长，或对 [aos, los] 全窗二次扫。

### P3-3 ✅ 预测缓存回填丢失 isGeo 标记

- **位置**：[SatellitePredictCacheStore.kt:41-58](../app/src/main/java/com/example/hamkit/data/satellite/SatellitePredictCacheStore.kt#L41-L58)
- **要点**：`SatelliteInfo` 重建时未持久化/恢复 `isGeo`；GEO 卫星缓存项按普通过境展示，提醒调度时序与前次可能错开导致重复通知。
- **修复方向**：save/load 序列化 isGeo 并在回填时还原。

### P3-4 ✅ FT8 自动 QSO 记录缺 myCall==peer 收尾分支

- **位置**：[Ft8ViewModel.kt:207-229](../app/src/main/java/com/example/hamkit/ui/viewmodel/Ft8ViewModel.kt#L207-L229)
- **要点**：对方发送「我的呼号 我的呼号 RR73/73」（FT8 常见收尾）落入 else 丢弃；含 reportSent 但缺 summary 的会话永远无法标完成。
- **修复方向**：新增 `call0 == myCall && call1 == myCall` 分支处理 RR73/73/RRR。

### P3-5 ✅ FT8 解码循环未与 15 秒 UTC 时隙对齐

- **位置**：[Ft8Recorder.kt:151-162](../app/src/main/java/com/example/hamkit/data/ft8/Ft8Recorder.kt#L151-L162)
- **要点**：`delay(1000)` 轮询槽号，检测到变化后取「最近 15 秒」数据；轮询抖动/阻塞 >1s 时窗口跨槽切割，Costas 同步分数下降。
- **修复方向**：按 `(slotIndex+1)*15000 - now` 精确 delay 到下一槽边界。

### P3-6 ✅ 音源设置持久化为播放捕获后，投影失效时显示与实际收音脱节

- **位置**：[SstvViewModel.kt:388](../app/src/main/java/com/example/hamkit/ui/viewmodel/SstvViewModel.kt#L388)

- **修复方向**：回退发生时把 audioSourceKind 回写 MIC 并同步 UI。

### P3-7 ✅ 权限状态机只认 FINE，与 LocationHelper 口径不一致

- **位置**：[PermissionManager.kt:74-90](../app/src/main/java/com/example/hamkit/permission/PermissionManager.kt#L74-L90) vs [LocationHelper.kt:45-54](../app/src/main/java/com/example/hamkit/data/location/LocationHelper.kt#L45-L54)
- **要点**：Android 12+ 用户选「大致位置」后定位功能可用，但权限页恒显示未授权且无法改变。
- **修复方向**：两处口径统一（FINE||COARSE），或 PermissionState 区分 coarse/fine。

### P3-8 ✅ 过境提醒直达接收态（autoStart）未校验通知权限

### P3-9 ✅ Navigator Saver 空栈兜底回退到未注册的 Route.Home
